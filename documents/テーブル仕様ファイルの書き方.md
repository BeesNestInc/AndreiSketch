# ads-schema/tables/ の書き方（テーブル仕様ファイル）

`ads-schema/tables/` には、Amazon Ads のレポートから取得したデータを Postgres に投入するための **テーブル仕様ファイル（1テーブル=1ファイル）**を置く。
この仕様ファイルを唯一の真実（single source of truth）として、以下を自動生成する。

* PostgreSQL DDL（CREATE TABLE / INDEX）
* UPSERT SQL（ON CONFLICT DO UPDATE）
* レポート取得リクエスト雛形（report request JSON）

## 1. ファイル配置と命名

* 置き場所：`ads-schema/tables/`
* 形式：JSON
* 1ファイル=1テーブル
* ファイル名：原則 `テーブル名.json`
  例：`sp_campaign_daily.json`, `sp_search_term_daily.json`

> 注：スクリプト側が `--table sp_campaign_daily` を基準に探すため、基本は **テーブル名とファイル名を一致**させる。

---

## 2. 最小構成（必須フィールド）

各ファイルは次の構造を持つ。

```json
{
  "name": "sp_campaign_daily",
  "report": {
    "adProduct": "SPONSORED_PRODUCTS",
    "reportTypeId": "spCampaigns",
    "timeUnit": "DAILY",
    "groupBy": ["campaign"]
  },
  "columns": [
    { "name": "profile_id", "type": "bigint", "null": false },
    { "name": "date", "type": "date", "null": false, "source": "date" },
    { "name": "campaign_id", "type": "bigint", "null": false, "source": "campaignId" },
    { "name": "impressions", "type": "bigint" },
    { "name": "clicks", "type": "bigint" },
    { "name": "cost", "type": "numeric(12,2)" },
    { "name": "raw_run_id", "type": "text", "null": false },
    { "name": "ingested_at", "type": "timestamptz", "null": false, "default": "now()" }
  ],
  "unique": [["profile_id", "date", "campaign_id"]],
  "indexes": [["profile_id", "date"], ["campaign_id"]]
}
```

---

## 3. フィールド仕様

### 3.1 `name`（必須）

* PostgreSQLのテーブル名（スキーマは別途固定：例 `ads`）
* 例：`sp_campaign_daily`

### 3.2 `report`（必須）

Amazon Ads Reporting API v3 のレポート作成リクエスト（configuration）に対応する。

* `adProduct`：例 `SPONSORED_PRODUCTS`
* `reportTypeId`：レポート種別（例 `spCampaigns`, `spSearchTerm` など）
* `timeUnit`：基本 `DAILY`（日次）
* `groupBy`：集計単位（例 `["campaign"]` など）

> 注：`timeUnit = "DAILY"` の場合、`columns` に `date`（source/nameが `date`）を含めること。

### 3.3 `columns`（必須）

テーブル列を定義する。順序はそのまま UPSERT のパラメータ順に使われる。

各要素は次を持つ。

* `name`（必須）：DB列名（snake_case推奨）
* `type`（必須）：PostgreSQL型（例 `bigint`, `date`, `numeric(12,2)`, `text`, `timestamptz`）
* `null`（任意）：省略時は `true`
* `default`（任意）：DDLのDEFAULT式（例 `now()`、`0`、`''` など）
* `source`（任意）：Adsの列名。省略時は `name` をAds列名として扱う

#### 3.3.1 内部列（必須）

以下の3列は必ず定義する（Adsのデータには含まれないため取り込み時に付与する）。

* `profile_id`（bigint, not null）
* `raw_run_id`（text, not null）
* `ingested_at`（timestamptz, not null, default now()）

### 3.4 `unique`（必須）

UPSERT の `ON CONFLICT (...)` に使う一意キー。配列の先頭（`unique[0]`）がUPSERTの衝突判定に利用される。

例（キャンペーン日次）：

```json
"unique": [["profile_id", "date", "campaign_id"]]
```

> 重要：`unique` に含める列は、原則 **NOT NULL** 推奨。
> PostgreSQLのユニーク制約は、NULLを「互いに異なる」と扱うため、キー列にNULLが入ると rerun で行が増える原因になる。
> 例：`ad_group_id` や `keyword_id` が欠ける可能性があるなら、`default: "0"` などで埋めて NOT NULL に寄せる。

### 3.5 `indexes`（任意）

検索・集計でよく使う列に通常インデックスを貼る。形式は `["col1","col2"]` の配列を並べる。

---

## 4. `source` の考え方（命名ルール）

* DB列名は snake_case（例：`campaign_id`）
* Ads列名は camelCase が多い（例：`campaignId`）
* この差を `source` で吸収する

例：

```json
{ "name": "campaign_id", "type": "bigint", "null": false, "source": "campaignId" }
```

---

## 5. 典型的な追加手順

1. `tables/` に新しい `*.json` を追加
2. `node ads-schema/generate-artifacts.js` を実行して DDL/UPSERT/request を生成
3. request.json 駆動でレポート取得
4. `ingest-report.js` でDB投入（UPSERT）

# reportTypeId と groupBy の選び方

## 基本原則

* `reportTypeId` は「どんな種類のレポートか」（キャンペーン／ターゲティング／検索語／広告商品…）
* `groupBy` は「そのレポートをどの粒度で返すか」（campaign / adGroup / placement / searchTerm など）
* 使える `groupBy` は **reportTypeId ごとに決まっている**。許容されない値を指定すると 400 で弾かれる。([Amazon Ads][1])

> 重要：`timeUnit: "DAILY"` を使うなら、`columns` に `date` を必ず含める（そうしないと日次の識別ができない）。([Amazon Ads][1])

## まず何を見ればいいか（公式ドキュメント）

* Reporting v3 の概要（考え方・粒度の説明）([Amazon Ads][2])
* “Get started” の `groupBy` の説明（reportTypeごとに `groupBy` が異なる）([Amazon Ads][1])
* 各 report type のページ（campaign / targeting / search-term / advertised-product …）

  * 例：Campaign reports（groupByの例が出る）([Amazon Ads][3])
  * 例：Targeting reports（SPのターゲティング系）([Amazon Ads][4])
  * 例：Search term reports（検索語）([Amazon Ads][5])
* columns一覧（どんな `reportTypeId` があるかの入口）([Amazon Ads][6])

## 実務上の “だいたい3パターン” の作り方（Sponsored Products想定）

「生データを貯めて後でSQLで集計する」前提なら、まずは以下が核になります。

1. **キャンペーン粒度**（全体の費用・クリック・表示）

   * `reportTypeId`: `spCampaigns`
   * `groupBy`: まずは `["campaign"]`（必要なら placement/adGroup を追加検討）([Amazon Ads][3])

2. **ターゲティング粒度**（キーワード／ターゲット別）

   * `reportTypeId`: `spTargeting`
   * `groupBy`: report type ページで許容値を確認して選ぶ（例：campaign単位など）([Amazon Ads][4])

3. **検索語粒度**（searchTerm）

   * `reportTypeId`: `spSearchTerm`
   * `groupBy`: こちらも report type ページで許容値を確認して選ぶ（検索語はデータ量が増えやすい）([Amazon Ads][5])

（追加の定番）

* **広告商品粒度**（ASIN/SKU寄りの分析）

  * `reportTypeId`: `spAdvertisedProduct` 等
  * 入口：Advertised product reports ([Amazon Ads][7])

> 補足：最終的に「どの `groupBy` が許容されるか」は report type のページが一次情報です。`tables/*.json` を書く前に、対象ページで `groupBy` 値と取得可能 columns を確認してください。([Amazon Ads][1])

# NULL（欠損）を unique キー列に含めるときのルール

## なぜ問題になるか

PostgreSQL の UNIQUE 制約は、**NULL を「等しい」と扱わない**ため、uniqueキーの一部が NULL になると、同一概念の行が rerun で増殖する事故が起きやすい（UPSERTの衝突判定が効かない）。

このプロジェクトでは rerun でレコードが増えないことを重要視するので、**uniqueキーに入れる列は原則 NOT NULL**に寄せる。

## 推奨ルール（このリポジトリ標準）

1. **unique に入れる列は原則 `null: false`**
2. Ads 側で欠損し得る列（例：`adGroupId`, `keywordId`, `matchType` など）を unique に含めたい場合は、次で “欠損を値に畳む”：

   * 数値ID：`default: "0"` にして NOT NULL
   * 文字列：`default: "''"`（空文字）にして NOT NULL
3. ingest 側は「NULL→default」へ正規化される前提で運用する

   * 仕様（tables/*.json）に default を書き、DB側でも揃える
   * これで rerun が idempotent（再実行しても増えない）になる

### 例（Search term のキーを太くしたい）

* `keyword_id` が無いケースがあるが unique に含めたい → `null: false + default: "0"` で吸収
* `match_type` も欠ける可能性 → `null: false + default: "''"`

> 代替案（必要になったら）：unique に “式インデックス（COALESCE）” を使う方法もあるが、生成器が複雑になるので現状は採用しない。

## ルールの実務的な指針

* **最初はキーを太め**にして rerun を安定させる（後で削るのは簡単）
* データ量が爆発するテーブル（search term 等）は、必要なら

  * `indexes` を絞る
  * `columns` を減らす（“生を全部”よりも“核指標+識別子”）
  * retention（古い日付をアーカイブ）
    を後で入れる
